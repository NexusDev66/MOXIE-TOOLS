# 技术架构

## 1. 总览(无 API、同库、全自动)
```
[头部] cli/seed-tools.json ─┐
                           ├→ AI 清洗补全 → 权重打分 → 写 moxie_products(status=published, weight_score)
[新锐] 抓取目录站 ──────────┘                 │   (service_role key, 服务端)
                                            ↓  同一个 Supabase: sqvohgcwzhhsvkmyesvs
        预渲染脚本: 读库 → 烤进 moxie-*.html 模板 + JSON-LD + sitemap.xml → 部署
                                            ↓
        静态 UI(爬虫看到烤好内容;浏览器再用 moxie-supabase.js 做投票/评论/登录交互)
        + 定时自动生成 published SEO 文章
```

## 2. 数据契约(静态 UI 实际读的表 —— 改库表前必看 moxie-supabase.js)
- `moxie_products` where `status='published'`,默认按 `vote_count` 倒序(Phase 2 引入 `weight_score` 后改按它),带 `moxie_categories` 关联。唯一键:`slug`、`domain`。
- `moxie_articles` where `status='published'`,按 `published_at` 倒序。
- `moxie_categories`(10 个固定分类,slug 见 migration / 设计规范)。
- `moxie_comments` / `moxie_votes` / `moxie_profiles`:交互,客户端 anon + RLS。

## 3. 关键决定
- **同一个 Supabase,直接读写,不做内部 HTTP API**(上一版 T2/T6 的 API 是错的)。
- **写**(管道/脚本):服务端用 `SUPABASE_SERVICE_ROLE_KEY`(绕 RLS)。**读**(静态站):客户端 anon key + RLS。
- **权重排序**:新增 `moxie_products.weight_score`,定时重算;静态站 `moxie-supabase.js` 排序字段改为 `weight_score`(vote_count 兜底)。
- **SEO**:预渲染脚本产出带数据的静态 HTML + sitemap,这是 SEO 生效的前提(纯客户端渲染对爬虫无效)。

## 4. 技术选型
- 静态 UI:原生 HTML/CSS/JS(`moxie-*.html` + `moxie-styles.css` + `moxie-shared.js` + `moxie-supabase.js`),保留不重写。
- 管道 / 脚本:Node 24 ESM,放 `cli/`,Supabase 走 REST(`/rest/v1`)+ service key(参考 `cli/trend-scanner.js` 的 `sb()` 写法)。
- AI 清洗:复用 `src/lib/enrichment`(DeepSeek 默认),去掉 server-only 依赖或改造成 cli 可调。
- 预渲染:Node 脚本读库 + 模板字符串注入(或轻量模板),产出静态文件。
- 定时:GitHub Actions cron(参考 `.github/workflows`),secret 配在仓库设置/部署端。
- 部署:静态站 + 预渲染产物发到托管(Vercel,已修好)。

## 5. 环境变量(只在 .env.local / 部署端,绝不进仓库)
| 变量 | 用途 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | 公开,库地址 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 公开,客户端读 |
| `SUPABASE_SERVICE_ROLE_KEY` | **密钥**,管道写库 |
| `DEEPSEEK_API_KEY` | **密钥**,AI 清洗 |
| `SIMILARWEB_API_KEY` | **密钥**,流量门槛(Phase 2/3) |
