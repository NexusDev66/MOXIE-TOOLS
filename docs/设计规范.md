# 设计规范(红线 + 约定)

## 安全红线(不可破)
1. **密钥只在 `.env.local`(已 gitignore)或部署端 env**。绝不写进代码 / 文档 / commit / 对话。提交前自检无 `sb_secret` / `sk-` / service key 泄露。
2. **不提交 `node_modules`**(`.gitignore` 已含 `**/node_modules/`;`git add` 前确认)。
3. **写库用 service key 只在服务端 / cli**,绝不暴露到客户端(不带 `NEXT_PUBLIC_` 前缀)。

## 工作纪律(针对上一版"囤代码不上线"的教训)
4. **小步 + 部署优先**:一次只做路线图里一个小步;**部署 + 线上验证通过**才算完成、才下一步。本地跑过 ≠ 完成。
5. **真实性**:只声称真验证过的;没跑过的不说跑过、不预勾验收框。
6. **幂等**:所有入库/迁移脚本可重复跑(upsert on_conflict、`if not exists`),不怕跑第二遍。
7. **每次收工写开发日志**(见 `../开发日志/`)。

## 数据约定(对齐现有库 + 静态 UI)
8. `moxie_products`:`slug`、`domain` 唯一;写库前保证 domain 是裸域名(无协议/路径)。`tagline ≤ 30 字`;`tags` 每项 ≤ 8 字、≤ 8 个;`status` 用 `published`(上线)/`pending`(待审)。
9. 分类只用现有 10 个 slug:`llm / ai-assistant / ai-writing / ai-image / ai-video / ai-coding / ai-search / rag / agent / workflow`。新增分类要同步改种子 + UI。
10. **不覆盖人工维护的产品**:自动管道遇到已存在 domain 时,只更新/链接,不清空人工填的 category/内容(上一版复审 #13 教训)。

## 代码约定
11. cli 脚本:Node 24 ESM,Supabase 走 REST + service key,参考 `cli/trend-scanner.js`。
12. Next 修改前读 `node_modules/next/dist/docs/`(见 AGENTS.md,这是改版 Next)。
13. 复用旧库逻辑(enrichment/打分/截图/文章生成)前先确认它不依赖被推翻的"API 前提"。

## Git
14. 在分支上做,提交信息讲清"做了什么 + 为什么";末尾**不加** Co-Authored-By。
15. 未经明确同意不 push;修复也先本地 commit、等确认。
